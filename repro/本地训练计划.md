# 本地 5070 Ti Laptop 跑训练：任务过程与预计时间

> 机器：RTX 5070 Ti Laptop 12 GB（sm_120）+ Core Ultra 9 275HX + Intel AI Boost NPU。
> **本文所有秒数都是本机实测**（标注来源），推算项单独标「估」。

## 0. 实测基线（时间的唯一来源）

| 量 | 实测值 | 怎么测的 |
|---|---|---|
| 训练 bs=2，全图 600×400 | **31.8 s/epoch**（8.2 it/s），峰值显存 **6.00 GB** | stage1 连跑 16 epoch 的时间戳差分 |
| 训练 bs=4（官方值），全图 | **46 s/epoch** 稳态（382 ms/iter），单 epoch 含首轮 cuDNN 调优 **66 s**，峰值 **10.98 GB** | 用 `lolv1_cloud_stage1` 实跑 1 epoch |
| warmup epoch（bs=2） | **31–32 s** each | stage1 日志时间戳 |
| 进程启动 + 数据集解码缓存 485 图 | **~6 s**（一次性） | `train pairs: 485` 出现时刻 − 启动时刻 |
| 每 epoch 验证（eval15，15 张） | ~2 s | 含在 31.8 s 内 |
| 折叠出 slim + 存 ckpt | ~1 s | 存 best 时 |
| 预训练权重全套评估（PSNR/SSIM/LPIPS） | ~1 min（估） | `evaluate.py --config lolv1_pretrained` 实跑 |
| slim 推理 600×400 | **每帧同步 1.204 ms（830 FPS）**；连续 100 帧只在末尾同步 = 0.994 ms（1006 FPS，掩盖了 kernel 启动开销）；被训练抢卡时中位 **3.27 ms** | `measure_latency`（每帧同步）+ 微基准（流水线） |
| LOLv1 下载（350 MB / 1000 文件） | **1 min 44 s** | hf-mirror 实下 |
| 算法自检 15 项 | ~20 s | `selfcheck.py` |

**关键一条，别再搞错**：本机 **bs=4 比 bs=2 每样本慢 57%**（0.0955 vs 0.061 s/样本）。
训练图是多分支 concat 造成的**带宽瓶颈**，加大 batch 不省钱，只是把官方配置抄下来。
所以本地跑请用 bs=2；bs=4 只在云端 24 GB 卡上才有意义。

## 1. 任务分解（每件事的过程与耗时）

### T1 · stage1（W_pre）：10 warmup + 1000 epoch，bs=2
**8.9 h**（10×31.8 s + 1000×31.8 s + 6 s 启动 ≈ 8.85 h）
过程：建 venv-free 直跑 → 解码 485 对入 RAM → warmup（DropBlock 双头自监督，val PSNR 只会 2–3 dB，正常）→
主训练（Adam 1e-3 + cosine-restarts，每 epoch 存 `state_last.pt`，刷新 best 时同时落 `model_best.pkl` + `model_best_slim.pkl`）→
第 50/150/350/750 epoch 处 loss 出现台阶（调度器重启，对应论文 Fig.10 的振荡）。
产物：`runs/lolv1_stage1/ckpt/model_best.pkl` = **W_pre**，`metrics.jsonl` 1010 行。

### T2 · stage2（IWO）：1000 epoch，bs=2
**8.8 h** → **T1+T2 合计 ≈ 17.8 h**
过程：建 IWO 图 → 把 stage1 权重灌进冻结的 `conv_out.weight`、`W_learn` 置零 → **epoch 0 的 val PSNR 必须等于 T1 的 best**（迁移正确的硬判据，日志会打印）→
续训 1000 epoch。产物：`runs/lolv1_stage2_iwo/ckpt/`。

### T3 · 无 IWO 对照组：2000 epoch 一口气
**17.6 h**（这是验证论文 Fig.10「后期停滞」claim 的唯一办法）

### T4 · 评估与报告（可中断、随时重跑）
每档 ~1 min + 最终报告 ~1 min → **合计 <10 min**。含空闲卡上重测延迟（拿干净的 0.9 ms 级数字）。

### T5 · UIE / UIEB（若之后要做）
800 对 620×460（面积是 LOLv1 的 1.18×）→ 每 epoch 400 iter × 0.122 s × 1.18 ≈ **58 s/epoch（估）**，
两阶段 1000+1000 ≈ **32 h（估）**。全图直训太贵，**必须改用随机裁剪或缩放到固定尺寸**
（256 裁剪按实测 135 ms/iter(bs=8) 算：800 对 → 100 iter → **13.5 s/epoch**，
但验证 90 张全分辨率还要 ~12 s → **25.5 s/epoch**，两阶段约 **14 h（估）**）；
LOLv1 用同样裁剪是 61 iter → 8.2 s + 2 s 验证 → 10.2 s/epoch，两阶段约 5.7 h。

### T6 · ISP / ZRR（当前不可训）
数据已完整（train 46,839 / test 1,204 块，448×448）。**Table 3 已核对完**：PSNR **21.438** vs 论文 21.43、
SSIM **0.7312** vs 0.731（作者权重，1 分钟）。ISP 网络与 Bayer loader 也已接进复现层
（`model.task: isp` + `data.kind: raw`，折叠误差 3.6e-07）。
从零训练：按论文 256×256 Bayer 口径估 **≈10 h**（两阶段 1000+1000）；注意 46,839 块全过一遍
是 23,420 iter/epoch ≈ 490 s，所以「epoch」要按每轮抽样的块数定义。

## 2. 三种排期，按需挑

| 方案 | 内容 | 本地总时长 | 拿到什么 |
|---|---|---|---|
| **最小可交付** | T1 + T2 + T4 | **≈ 18 h** | 从零复现 LLE 两阶段 + IWO 增益，可对表 Table 1 |
| **完整（推荐）** | T1 + T2 + **T3** + T4 | **≈ 35.5 h（1.5 天）** | 上面 + Fig.10 对照曲线（论文最核心那张图的正经复现） |
| **全任务** | 完整 + T5 + T6 | **≈ 68 h（2.8 天）全图**；T5 改 256 裁剪则 **≈ 43 h** | 三任务全上（UIEB 尺寸策略待定，ZRR 只评估） |

**分时段示例**（完整方案，白天要用机器的排法）：

```
D1 20:00  nohup 挂上 run_two_stage.cmd        (T1+T2 自动串联)
D2 08:00  T1+T2 完 → 评估 + 中间报告（此时已可对表 Table 1）
D2 09:00  白天用机 → 想停就停（最多损失当前 1 个 epoch = 32 s）
D2 20:00  挂 T3 对照 (17.6 h)
D3 14:00  全部完成 → report.py 出终版
```
每档产物都独立可用：只跑完 T1 就已经有"从零训出来的 4K 参数模型"可以评估（约 23.0±0.3 dB）。

## 3. 过程纪律（怎么不白等）

根目录有一个一键入口 `run.cmd`（它负责后台启动、进度显示、停止、评估、出报告）：

```bat
run.cmd              :: 启动 T1→T2 链路（脱离窗口，崩了自动从 state_last.pt 续，最多 4 次）
run.cmd status       :: 进度条 + 实测 s/epoch + 剩余小时 + 预计完成时刻 + 最新 best
run.cmd watch        :: 每 30 秒刷新
run.cmd stop         :: 停止（断点保留）
run.cmd verify       :: 官方权重对齐论文 Table 1（约 1 分钟，不训练）
run.cmd eval         :: 评估现有 ckpt（训练图会自动折叠再对一次）并出报告
run.cmd report       :: 只重生成 results\report.md
```

`status` 的真实输出（截自本机，当时 26/1010 epoch）：

```
 GPU 利用率 12%   显存 845 MiB   功耗 29.49 W
 lolv1_stage1      stage1 [....................]   2.6%  26/1010 ep  已停
   32.0 s/epoch → 剩 8.75 h，约 09-27 01:29 完成
   最新 ep16 loss 0.7116 val_psnr 16.880
   best val_psnr 18.363 @ ep8   (论文 Table 1 LOLv1 = 23.62 dB)
   最后一条记录 110 分钟前 → 进程疑似已停，续跑：run.cmd start
 lolv1_stage2_iwo  stage2 未开始（1000 epoch，约 8.9 h）
 链路合计剩余 ≈ 17.64 h，约 09-27 10:22 全部跑完
```
它只读盘上的 `runs/*/metrics.jsonl` + `logs/runner.log`，不跟训练进程通信，所以训练是手起的、
或 runs/ 是从别的机器拷回来的，它照样能算；判定「运行中/已停」的依据是最后一条记录的年龄
（>3× s/epoch 视为已停）并直接给出续跑命令。

**实时看板**（推荐挂着它）：`run.cmd board` → `http://127.0.0.1:8765`，
按钮触发 + 每 3 秒刷新曲线/进度/ETA/GPU/日志；只绑 127.0.0.1，因为它能启停进程。

一个要知道的细节：重跑同一条配置时 `make_run` 会加时间戳后缀（如 `runs/lolv1_stage1_190523`），
所以**新链路写在带后缀的目录里**；状态解析按「最新的 metrics.jsonl」自动跟随，看板会用红字
标出它实际跟的是哪个目录，不会把旧目录当成在跑。

手工等价命令（`run.cmd` 内部就是这些）：

```bash
cd repro && cmd //c 'start "" /min scripts\run_two_stage.cmd lolv1_stage1 lolv1_stage2_iwo'
tail -f logs/lolv1_stage1.log
python scripts/train.py --config lolv1_stage1 --resume lolv1_stage1     # 原地续跑
```

**中断与恢复**：`--resume lolv1_stage1` 原地续跑（权重 + Adam 矩 + cosine 周期位置 + best + RNG 全在
`state_last.pt` 里，73 KB/epoch）。实测续跑 loss 不回弹（1.904→1.730）。

## 4. 本地跑的四个真实风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **睡眠/合盖** | 进程挂死或被系统回收（上次 16 epoch 就是这么没了） | 插电；电源设置把交流睡眠超时设 0：`powercfg /change standby-timeout-ac 0`（**这条改你系统设置，我不擅自动手**，你自己跑或明说让我跑） |
| 过热降频 | 总时长 +10~30% | 垫高/开风扇模式；别同时玩游戏（`GameViewer`、`wallpaper32` 都在占 GPU） |
| 显存争抢 | bs=2 只用 6.0 GB，余量充足；bs=4 只剩 1.8 GB 余量，别开本地大模型 | 本地坚持 bs=2 |
| 测速数字被污染 | 抢卡时同一份权重延迟 0.99→3.27 ms | 所有延迟/FPS 测量放在空闲时；报告里 `measure_latency` 同时给 best/median |

## 5. 本地 vs 云端一句话总结

| | 本地 5070 Ti Laptop | 云端 4090（24 GB） |
|---|---|---|
| 完整方案（T1+T2+T3） | ≈ 35.5 h，¥0，机器被占 1.5 天 | 推算 **18–26 h ≈ ¥40–57** |
| 只两阶段（T1+T2） | ≈ 17.8 h，¥0，一夜 | 推算 **9–13 h ≈ ¥20–29** |
| batch | 只能 bs=2（偏离官方 1 项） | 能跑官方 bs=4（偏离减 1 项） |
| 数据/代码迁移 | 0（已就绪） | 一条 `pack.ps1` + 一次 scp（336 MB 包已审计） |
| 中断恢复 | `state_last.pt` + 自动重试 | 同 + `sync_back.ps1` 每 5 分钟拉回本地 |

**如果只是想拿到能写进报告的忠实数字**，云端更划算（省 1.5 天占用 + 修掉 batch 偏离）；
**如果不想花钱也不想折腾上传**，本地按上面分时段排两个晚上就能跑完，风险点只有睡眠和散热两个，都可控。
